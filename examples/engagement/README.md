# A worked engagement

One customer, start to finish, with the artefacts it produced. Everything here
was generated by the commands below against the warehouse in `warehouse.sql` —
nothing was written by hand to look good, and you can regenerate all of it.

```bash
createdb conglomerate && psql -d conglomerate -f warehouse.sql
export CONGLOM_DSN="postgres://…/conglomerate?sslmode=disable"

di survey -out out/survey.md     # ① what is actually in there
di model gen -dsn "$CONGLOM_DSN" -out models/warehouse.yaml
                                 # ② a draft, then edit it — see below
di eval                          # ③ every metric against a control query
di report                        # ④ the handover document
di handover                      # ⑤ runbook + CI gate
di drift                         # ⑥ run this on a schedule from now on
```

After step ①, none of the commands take arguments: `engagement.yaml` is the
configuration, so what a colleague runs is what you ran.

|---|---|---|

## ① The survey found the thing nobody would have mentioned

```
7 tables, 4,964 rows in total
4 tables all stop at 2025-12-01: overheads, procurement, sales, shrinkage
  — one event, not 4 problems. A load that stopped, or a migration nobody mentioned?
```

Every row in those tables is valid. Nothing errors. The totals have simply not
grown since December, so "how did we do last month" answers a question about a
month eight months ago, cleanly and wrongly.

Note what the survey does **not** say. `stores` has ten rows and last opened in
2022; that is a chain that stopped expanding, not a broken feed, and a check
that flags it teaches people to skim the section it most needs them to read.

## ② The generated draft, and the part a person still has to do

`di model gen` reads the foreign keys and produces 7 entities, 8 joins, 13
dimensions and 26 metrics — including the ratios that come from one table:

```yaml
sale_gross_margin            = (sale_revenue_sum - sale_cogs_amount_sum) / sale_revenue_sum
sale_revenue_per_transaction = sale_revenue_sum / sale_transactions_sum
```

Two more were added by hand, and they are the interesting ones because a
generator cannot know they are wanted:

```yaml
shrinkage_rate = shrinkage_loss_amount_sum / sale_revenue_sum   # two fact tables
sales_per_sqm  = sale_revenue_sum / store_area_sqm_sum          # fact ÷ dimension attribute
```

Both cross tables. Which two things are worth dividing is a business question,
and a generator that guessed would produce plausible metrics nobody asked for.

### Why `sales_per_sqm` is the one to look at

Floor area lives in `stores`, one row per shop. Joining it to `sales` repeats
each shop's area once per sales row — 144 of them — and inflates the
denominator:

```
semantic layer   16,191.71
naive join          112.44      ← 144× too small
```

The naive query runs clean. It returns a number. The number is wrong by two
orders of magnitude, and nothing in the output says so. That is the failure this
whole layer exists to make impossible: the compiler aggregates each measure to
its own grain in its own CTE and only then joins, so the inflation cannot happen.

## ③ Six metrics reconcile — and the report says they are only self-consistent

```
[PASS] sale_revenue_sum              235184659.92
[PASS] sale_gross_margin             0.2346
[PASS] sale_revenue_per_transaction  134.9217
[PASS] shrinkage_rate                0.0316
[PASS] sales_per_sqm                 16191.715
[PASS] store_count                   10
[GAP]  22 metric(s) have no control query
eval: 6/6 passed (6 of 28 metrics covered)
```

Every control query here was written by the same person who wrote the metric, so
each case records `source: engineer` and the delivery report says:

```
PARTIAL — 6/28 metrics reconcile, 22 have no control query,
          none is anchored to a customer figure
```

Not `VERIFIED`. Two controls written from the same misunderstanding agree with
each other, and agreement is not correctness. On a real delivery these lines get
replaced with figures the customer already publishes — their board pack, their
finance system — and `source: customer-report` says which. That is the line
between verification and theatre, and the report draws it for you.

## ⑤⑥ Day 2

`di handover` writes the runbook for whoever inherits this: which databases are
governed and what that means, what to run when someone says a number looks
wrong, and — the part that is not the tool's to decide — what a metric means,
who may see it, and whether a feed is allowed to stop.

It also writes a CI workflow wiring `${CONGLOM_DSN}` to a repository secret of
the same name, because a gate that has to be remembered is a document.

`di drift` is what runs afterwards. It exits non-zero, so it works as a
scheduled job:

```
DRIFT — 4 feeds all stopped on 2025-12-01
  4 feeds all stop at 2025-12-01: overhead_month, procurement_month, sale_month,
    shrinkage_month — one event. A load that stopped, or a migration?
  employee_hire_date stops at 2023-04-11 (1210 days ago)
```

## What this engagement fed back

`engagement.yaml` ends with a `delta:` section — what the platform could not do.
Recording it is what separates an engineer from a consultant: a consultant
finishes and leaves, and the next delivery costs the same.

```yaml
delta:
  - kind: missing-feature
    what: cross-table ratios are not proposed by the generator
  - kind: data-issue
    what: every fact table stops at 2025-12-01
```

`di delta -root ~/engagements` counts these across customers, most repeated
first. One is a workaround; the third person to hand-roll the same thing is the
expensive one. The single-table ratios in step ② exist because a previous
engagement recorded exactly that gap.

## The data

Synthetic, and deterministic — `warehouse.sql` builds it from `generate_series`,
so the figures above are the figures you will get. Two properties are not
incidental: the fact tables stop at 2025-12-01 so the survey has something real
to find, and `stores` is small enough that its old `open_date` must *not* be
reported as a stopped feed.
